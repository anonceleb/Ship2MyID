Merchant console — Alba Goods

Everything you need to run deliveries. Nothing you're structurally able to see.

This is the exact shape of what the Ship2MyID merchant SDK returns — no more. Every number below comes from a live session running in your browser; where a customer's address would normally sit, you'll find why it can't.

Shipments

Shipments in flight

Every row below is exactly what checkout() handed back at the moment the order was placed — an opaque recipient reference, an operator, a promised delivery window. Nothing else was ever received.

Status is a pull, not a push. Nothing calls back to this console on its own — Ship2MyID's notification port is addressed to the buyer, never to a merchant participant id. But you can always ask: status below comes from a real getCapabilityStatus() read, ownership-checked against this participant id, run fresh on every render. It is deliberately three states — issued, revoked, expired — never "out for delivery." Nothing tells this console that either, on purpose.

Recipient is a pairwise S2ID — a fresh, unrelated code for every merchant that ever transacts with the same buyer. See the Consumer flow for how it's derived and why it can't be matched back to a person.

Signing key fingerprint

There's no bearer token to leak — every request is signed locally with an Ed25519 key, the same way packages/registry verifies it on arrival. The fingerprint above is a real, freshly generated key for this browser session; only its public half would ever be registered with the network. Ship2MyID never receives, stores, or can reconstruct the private half.

SDK snippet

// The entire merchant-facing surface. No address parameter exists to pass. import { MerchantClient } from "@ship2myid/sdk"; const client = new MerchantClient({ platform, participantId: "alba-goods.example", keyId: "k1", privateKey: process.env.SHIP2MYID_PRIVATE_KEY, }); const result = client.checkout( { s2id, weightKg: 2, carrier: "MER-POST", destinationKind: "locker" }, subjectRef ); // result: { s2id, capabilityId, geoBucket, serviceLevel, // estimatedDelivery, verifiedHuman } // Pull a status read at any time — ownership-checked, three states only. client.getStatus(result.capabilityId); // { status: "issued" | "revoked" | "expired" } // Register once; every settlement fires a signed POST from then on. client.registerWebhook({ url: endpointUrl, secret });

This is the published SDK's actual call shape, not illustrative pseudocode — a hosted API wraps the same contract 1:1.

Webhook configuration

Endpoint URL
Events

Registering performs a real, signed fetch() POST to the URL above — an HMAC-SHA256 signature over the same canonical JSON packages/registry uses to sign request envelopes, retried up to 3 times, exactly what packages/webhooks does server-side. Most browsers block cross-origin delivery to an arbitrary URL by design (CORS) — a failed attempt below is that working correctly, not a bug in this page. From then on, every checkout attempt you run on the Policy tab fires the same delivery for real.

Policy

One signed, versioned rule governs every checkout you attempt. Everything else your buyers never had to hand over isn't a setting you can toggle — it was never representable in the first place.
